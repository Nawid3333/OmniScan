## State in one paragraph
**This session found and fixed three real performance/correctness bugs in the OCR/translation path, then changed the translation default on the owner's instruction.** In order: (1) the OCR qualification suite (O1c, merged) was rebuilding its VRAM manager per chapter instead of per candidate, and a `series.toml` was silently clobbering the candidate's OCR config at two separate merge points — both fixed directly by the director (`core/stage.py`, `eval/qualify.py`), since one crossed into `core/**`. (2) PaddleOCR-VL's shipped `generation_config.json` had `use_cache: false` inherited from training, so every generation step recomputed the whole sequence; forcing `use_cache=True` (and *not* batching — measured 9-32x slower batched, reversing an earlier assumption) took real chapters from 749-864s to 56-100s at identical quality (`docs/benchmarks/ocr-qualification-results.md`). A side effect: long text blocks silently truncated at `vl_max_new_tokens` were being scored as fully trustworthy — now scored 0.0 so `ocr.drop_conf` filters them. (3) Ollama's own context-length setting (256K on this machine) was pushing 11 of translategemma:12b's 49 layers onto the CPU, and two local models were staying resident in VRAM at once; OmniScan now sends its own `num_ctx` and unloads every other local Ollama model before using one (`llm/ollama.py`, `pipeline/stages.py`) — translate stage 83.7s → 60.9s on a real chapter. Ran a real translation-model comparison (translategemma 12b/27b, gemma4 12b/31b, gemma4-31b-cloud, several judge combinations) against 5 real Pepper&Carrot chapters with official English text: the cloud model alone matches every judged ensemble and is 3-6x faster; the bigger local models don't fit in 16 GB VRAM and are both slower and no better (`docs/benchmarks/translation-model-comparison.md`). **Owner's decision: `gemma4:31b-cloud` alone is now the only enabled translation profile**, with `translategemma:12b` wired as its automatic fallback for when the cloud rate limit is hit (`TranslationProfile.fallback`, `resolve_fallbacks`, `TranslateStage`/`JudgeStage` rate-limit handling) — a chapter that falls back is retried against the cloud model on the next run. ## How to work the loop (for the next session)
- **Builders:** `uv run python scripts/omni_builder.py run <ID>` from `V:\OmniScan` (default `glm-5.3-flash:cloud`). Launch as a **background tool call**. Worktrees go to `V:\OmniScan-wt\<ID>`. **`git worktree remove --force` can leave an empty directory behind**, which fools `omni_builder.py`'s `is_dir()` check into skipping `git worktree add` — always `rm -rf` the leftover directory before retrying (hit this session). A builder that ends at its turn limit has usually finished the work but not committed — check `git status` in its worktree first.
- **Card → review → merge:** write `docs/tasks/<ID>.md` (exact interfaces, numbered acceptance tests, file allowlist, stop-and-ask rule — the O1e/TL1 level of detail); after the builder finishes: `git rebase main` in the worktree, read `docs/reports/<ID>.md` in full (the Questions section catches real spec bugs), run ruff/pyright/pytest, **spot-check anything security- or measurement-critical yourself** (this session: re-verified TL1's rendered zh/ja prompts by hand rather than trusting the report's description), look at real output where it's visual, `git merge --ff-only`, push, remove the worktree and branch.
- **Core-owned edits held across a card:** when a card needs a `core/**` change the builder can't make (this session: O1e's second `series.toml` re-merge lived inside `core/stage.py::make_context`), the director makes that fix directly and flips the builder's "pin the bug" tests to their post-fix assertions in the same review pass — don't leave `main` red waiting for a second card.
- **No concurrent heavy tasks.** Never run multiple heavy processes (pytest suites, GPU pipelines, real-hardware benchmarks) at once — it starves everything (looks like a hang) and invalidates any timing data collected during the overlap. Established as a hard rule this session after CPU contention from redundant concurrent test runs made a builder look stuck for 2+ hours.
