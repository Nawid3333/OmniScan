# G3 — Steady GPU load, part 2: find and remove the idle gaps around the stages

**Owner:** GLM builder · **Branch:** `G3` · **Worktree:** `V:\OmniScan-wt\G3` · run with `--max-turns 300`
Read `CLAUDE.md`, then `docs/GPU_NOTES.md` (what we measured and why), `docs/reports/G2.md` (what G2 already did: `gpu/warmup.py`, faster typeset fit), `src/omniscan/gpu/groups.py`, `src/omniscan/pipeline/`, `src/omniscan/inpaint/`, `src/omniscan/detect/`.
This card is a goal, not a spec: you investigate, decide and implement; the acceptance evidence at the bottom is what counts.

## Why
The owner hears **coil whine** from the RX 9070 XT while OmniScan runs: the GPU load is bursty (long idle gaps, then short bursts, CPU-bound phases in between). A steady load is a product requirement. G2 hid the first-conv/FFT/GEMM stalls in a background warm-up thread and made typeset fit 4.5x faster. What is left, measured by the director on `omniscan run PepperCarrotKR -c "Episode 06" --force -s ingest -s slice -s detect -s ocr -s inpaint -s inpaint_lama -s typeset -s export` (fresh process, G2 merged):

| item | measured |
|---|---|
| stage timers (sum) | 19.4 s (`slice` 8.3, detect 3.1, ocr 3.7, inpaint 0.7, inpaint_lama 1.1, typeset 1.5, export 0.8) |
| process wall clock | **67.5 s** — ~48 s are outside every stage timer |
| `slice` | 8.3 s for a CPU-ish stage that took 1 s before G2: it now waits for the warm-up thread (the 11.7 s library load is unavoidable, only its position moved) |
| model group `inpaint` | `loading model group inpaint` at 19:44:11, `warming up LaMa` at 19:44:28: **~17 s** to load a ~2 GiB group (disk? unpickling? CPU->GPU copy? contention with the warm-up thread?) |
| after that | LaMa "warm-up of the fixed window shape (one-time, 10-25 s)" — G2's warm-up thread already covers the FFT plans/conv init, so this may now be redundant or overlappable |
| process start | imports, config, catalog, model resolution: not measured yet |

## Goal
Make the wall clock of that command approach the sum of real work (target: **<= 35 s**, stretch 25 s) and remove every idle gap >= 1 s during which the GPU has nothing to do while the CPU could be preparing the next stage. **Outputs must stay bit-identical.**

## Method (in this order)
1. **Measure first, wall-clock only.** Add a tiny timeline facility (your design; e.g. `omniscan.gpu.timeline` with `mark(name)` + an env var or `--timeline` to print/write it) or use plain `time.perf_counter` logging — but **never `torch.profiler`** (on this ROCm-Windows stack it perturbed a run and produced a corrupted export; never keep output from a profiled run). Produce the table "where do the 48 s go" (imports, config/catalog, each model-group load, each warm-up, each stage, idle gaps).
2. Optionally sample real GPU utilisation while a run is going (Windows: `typeperf "\GPU Engine(*)\Utilization Percentage"` or `Get-Counter`; pick the engine of the 9070 XT, the iGPU is `cuda:0`). A `scripts/gpu_timeline.py` that prints utilisation per second next to the stage boundaries is welcome (evidence for steadiness), not mandatory.
3. Attack the biggest gaps first. Ideas, not orders: start the warm-up thread at CLI/process start instead of at `build_vram_manager`; load the *next* model group (weights disk -> pinned memory -> GPU) in a background thread while the current stage computes; find why the `inpaint` group takes 17 s to load (mmap/safetensors, unpickling, dtype conversion, redundant copies) and fix the cause; skip the LaMa "warm-up" when the G2 warm-up already ran the same ops; run ingest/slice CPU work while the GPU stage of the previous chapter runs (only if it stays simple and deterministic).
4. Re-measure after every change; keep only changes that help (say so in the report when one does not).

## Constraints
- Do not edit `src/omniscan/core/**` (director-owned; if a contract must change, stop and describe it in the report). Do not change model weights, precision (fp32 only on this stack) or algorithms; no CPU fallbacks; tensors stay on the GPU between steps.
- Threads: the ROCm-Windows stack is fragile. Any new background thread must be daemon, exception-safe (a failure logs a WARNING and the main path still works) and switchable off (`cfg.gpu.warmup`-style flag in an existing `GpuConfig` field if one fits, otherwise ask in the report — config is director-owned).
- Other builders may run GPU tests at the same time and disturb timings: repeat each measurement 3x and report min/median.
- Tests use synthetic fixtures; real chapters live in `data/raws/` (never commit them, never write intermediate images to disk).
