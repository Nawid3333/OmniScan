# P2 — CI matrix: `uv sync --extra cpu` + the full CPU test suite on Windows/Linux/macOS

**Owner:** GLM builder · **Branch:** `P2` · **Worktree:** `V:\OmniScan-wt\P2` (created by `scripts/omni_builder.py`)
Read `CLAUDE.md` first. Then read `pyproject.toml` in full (the `cpu` extra this card exercises, and
`[tool.uv.conflicts]` — the whole reason a CI job must pick exactly one backend extra, never `--all-extras`)
and `.github/workflows/model-watch.yml` in full (the only existing workflow in this repo — the exact
`astral-sh/setup-uv@v6` action and general style to imitate; this card is a different, new workflow file, not
an edit to that one).

## Why
Card P1 (merged 2026-09-23) made the torch backend a per-machine choice (`rocm-gfx1201` / `cuda` / `cpu` /
`mps`), so the project can now, in principle, `uv sync --extra cpu` and run on any OS PyTorch supports — but
nothing has ever actually verified this outside the one AMD ROCm dev machine this repo has always run on.
`docs/PLAN.md`'s own P2 item is exactly this: prove `uv sync --extra cpu` plus the CPU test suite genuinely
works on Windows, Linux and macOS, in CI, not just in theory.

## The fix
New file `.github/workflows/ci.yml`:
```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  test:
    strategy:
      fail-fast: false
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    steps:
      - uses: actions/checkout@v5
      - uses: astral-sh/setup-uv@v6
      - name: Sync (cpu backend)
        run: uv sync --extra cpu
      - name: Test (CPU-only; no GPU hardware in CI)
        run: uv run pytest -m "not gpu"
      - name: Lint
        run: uv run ruff format --check . && uv run ruff check .
      - name: Type check
        run: uv run pyright
```
Adjust exact syntax as needed to match `setup-uv@v6`'s real interface (check its README/marketplace page if
unsure — this card's job is a working, green workflow, not a byte-for-byte copy of the sketch above) and
`model-watch.yml`'s conventions (e.g. if it pins a specific `uv` version via the action's `version:` input,
do the same here for reproducibility).

## Definitions (no interpretation needed)
- `--extra cpu`, never `--extra rocm-gfx1201`/`cuda`/`mps` and never `--all-extras` — GitHub-hosted runners
  have no GPU of any kind, and `--all-extras` would try to install all four conflicting torch backends at
  once, which `[tool.uv.conflicts]` correctly refuses (this is the exact failure mode P1 was designed to
  surface loudly instead of silently).
- `-m "not gpu"` excludes every `@pytest.mark.gpu` test — there is no GPU hardware in CI to run them on. Do
  not attempt to also run gpu-marked tests with `torch.device("cpu")` substituted in some way; that is a
  different, much larger effort (GPU-marked tests assume real accelerated kernels) and explicitly out of
  scope.
- The `gui` extra (PySide6) is **not** part of this card's sync command — Qt needs a virtual display (e.g.
  `xvfb` on Linux) to run headlessly in CI, which is real extra setup work; leave `tests/gui/**` to skip
  naturally (it already does when PySide6 isn't installed, exactly the behaviour every worktree without
  `--extra gui` already shows).
- If a test in the "CPU" suite turns out to need a live Ollama server or network access that CI genuinely
  cannot provide (nothing is currently marked `network` in `pyproject.toml`'s `markers`, so this would be a
  newly-discovered gap, not an expected one), do not silently skip or delete it — stop and write exactly
  which test and what it needs under Questions in the report; this is real information the director needs,
  not something to guess a workaround for.
- `fail-fast: false` is intentional: a failure on one OS should not cancel the other two jobs, since the
  whole point is comparing all three independently.

## Out of scope

`uv`'s downloaded wheels across CI runs for speed (a nice-to-have, not required for this card to be done),
publishing coverage reports or badges.
