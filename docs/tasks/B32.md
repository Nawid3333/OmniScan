## Why (found by the director, a real, current staleness)
`doctor.py`'s `REQUIRED_OLLAMA_MODELS` is a hand-maintained tuple: `("translategemma:12b", "gemma4:12b",
"gemma4:31b-cloud", "glm-5.3-flash:cloud")`. As of commit `079a1e5` (2026-09-23) this is already wrong:
`gemma4:12b`'s profile is `enabled = false` and used by nothing (not even a fallback target), so `doctor`
warns about a model the pipeline will never touch, while giving no special treatment to the models a real run
*does* need — `gemma4:31b-cloud` (the enabled profile) and `translategemma:12b` (its `fallback`, only used
during a rate limit, so its absence is a real but easy-to-miss risk). A hardcoded list will keep drifting
every time `config/translation_profiles.toml` or `config/judge.toml` changes; the fix is to compute the
required set from those files directly, the same way the pipeline itself resolves them.

## The fix (design decided by the director — implement this shape, not a different one)
Replace the hardcoded tuple with a function that derives the same information from the real config files:
```python
def required_ollama_models(
    profile_paths: Sequence[Path] | None = None, judge_paths: Sequence[Path] | None = None
) -> list[str]:
    """Every Ollama model name a real run can need: every enabled profile's model, every enabled profile's
    fallback (if it names one), and the judge's model — local models only (a `*:cloud`/`*-cloud` name is
    served by Ollama Cloud through the same local daemon, so it still counts; there is nothing to exclude
    here — every model in this list is checked the same way). Order: profiles first (in file order), then
    the judge's model if not already present. Duplicates removed, first occurrence kept.
    """
```
- Load profiles with `load_profiles(profile_paths or default_profile_paths())`, keep only `enabled` ones (as
  `pipeline/stages.py::build_stage` already does), resolve fallbacks with `resolve_fallbacks` against the
  *full* loaded dict (enabled and disabled — a fallback profile is allowed to be `enabled=false`, exactly
  like `translategemma-12b-local` is today), and collect each enabled profile's `.model` plus its fallback's
  `.model` when it has one.
- Load the judge with `load_judge_config(judge_paths or default_judge_paths())` and add `.model`.
- `check_ollama_models(cfg, http)` calls `required_ollama_models()` (no arguments — the real shipped/user
  files) instead of iterating the old constant. Keep the function's behaviour otherwise identical: same
  `CheckResult` shape, same "missing: a, b" WARN message, same "N models, all required present" OK message
  (`N` = the count from `/api/tags`, unchanged — only the *required* set changes, not how the message reports
  the total).
- **Keep `REQUIRED_OLLAMA_MODELS` as a module-level name** (existing tests reference `doctor.REQUIRED_OLLAMA_MODELS`
  directly) but make it `required_ollama_models()`'s result computed at import time from the *shipped* config
  files only (`default_profile_paths()[:1]`/`default_judge_paths()[:1]` — i.e. `config/translation_profiles.toml`
  and `config/judge.toml`, ignoring any per-user override file, so this module-level constant is deterministic
  and does not depend on the machine it runs on). `check_ollama_models` itself must call
  `required_ollama_models()` with **no arguments** (shipped + user, the real merged behaviour), not read the
  module constant — the constant is a fixed reference value for tests and any other caller that wants the
  shipped defaults specifically.

## Definitions (no interpretation needed)
- With today's shipped files, `required_ollama_models()` (no args) returns
  `["gemma4:31b-cloud", "translategemma:12b", "gemma4:31b-cloud"]` before dedup →
  `["gemma4:31b-cloud", "translategemma:12b"]` after (the judge's model is `gemma4:31b-cloud`, already
  present from the enabled profile, so it is not added again). Pin this exact list as a regression test
  against the real shipped files (no monkeypatching) — this is the concrete, current-reality check that would
  have caught today's staleness.
- A profile that is `enabled = false` and is **not** anyone's fallback contributes nothing (matches
  `gemma4-12b-local` today, correctly excluded).
- A profile that is `enabled = false` but **is** another profile's fallback (`translategemma-12b-local` today)
  **is** included — it can genuinely run.
- If loading either file raises (invalid TOML, a `resolve_fallbacks` `ValueError` for a broken fallback
  chain), `check_ollama_models` catches it the same way `check_models`/`run_all_checks` already handle
  exceptions elsewhere in this file: return a `CheckResult("ollama_models", "WARN", f"{type(exc).__name__}:
  {exc}")` rather than letting it propagate (a config error should not crash `omniscan doctor`).
