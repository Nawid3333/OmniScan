# F14 — `inpaint/patches.py`: make `load_patches` torch-free (defer `save_patches`'s torch import)

**Owner:** GLM builder · **Branch:** `F14` · **Worktree:** `V:\OmniScan-wt\F14` (created by `scripts/omni_builder.py`)
Read `CLAUDE.md` first. Then read `src/omniscan/inpaint/patches.py` in full (short file, the only one this
card touches) and `tests/unit/test_inpaint_patches.py` in full (the existing test style to match).

## Why
`src/omniscan/web/app.py` imports `load_patches` from this module to serve inpaint-patch PNGs to the debug web
viewer. `load_patches`'s own body only ever touches `numpy` — it never references `torch` at all. But the
module has a top-level `import torch` (needed only by `save_patches`, the pipeline-writer side, which really
does call `.cpu()`/`.permute()`/`.numpy()` on real `torch.Tensor`s), so merely importing this module — and
therefore merely importing `omniscan.web.app`, and therefore starting `omniscan serve` — transitively requires
torch to be installed and importable, even though the web server's own read path never needs it (flagged in
`docs/OPEN_QUESTIONS.md` from card B11b; not urgent today since every machine that runs this repo already has
torch, but a real gap if the debug viewer is ever meant to run standalone on a lighter machine).

## The fix
Move the `import torch` out of module scope into a `TYPE_CHECKING`-guarded import (for static type checking)
plus a local `import torch` inside `save_patches`'s own body (for runtime, only when that function is actually
called). `from __future__ import annotations` is already the first import in this file, so every annotation is
already a lazy string at runtime — the `torch.Tensor` references in `save_patches`'s signature need no quoting,
they only need `torch` to be resolvable by pyright, which the `TYPE_CHECKING` block provides. Exact shape:

```python
from __future__ import annotations

import os
import tempfile
from collections.abc import Mapping
from pathlib import Path
from typing import TYPE_CHECKING

import numpy as np

if TYPE_CHECKING:
    import torch

_PIXELS_SUFFIX = ".pixels"
_MASK_SUFFIX = ".mask"


def save_patches(path: Path, patches: Mapping[str, tuple[torch.Tensor, torch.Tensor]]) -> None:
    """... (keep the existing one-line docstring, unchanged)"""
    import torch  # local: only this function needs torch; load_patches (used by the web server) must not

    arrays: dict[str, np.ndarray] = {}
    ...  # rest of the function body is byte-for-byte unchanged
```
`load_patches` itself is not touched at all — it already has no `torch` reference anywhere in its body.

## Definitions (no interpretation needed)
- "Torch-free" means: a fresh Python process that imports `omniscan.inpaint.patches` (or anything that only
  transitively needs `load_patches`, like `omniscan.web.app`) never adds `"torch"` to `sys.modules` unless
  something else in the same process already imported it first. Checking this **in the current test process**
  is not a valid test — pytest's own collection, or an earlier test file, may already have imported torch into
  the shared process, which would make the assertion trivially (and wrongly) pass. The real test spawns a
  **separate** Python subprocess (`subprocess.run([sys.executable, "-c", "..."], capture_output=True, check=True)`)
  that imports only `omniscan.inpaint.patches` and asserts `"torch" not in sys.modules` from inside that fresh
  process, failing loudly (non-zero exit / raised AssertionError shows in the subprocess's stderr) if it isn't.
- `save_patches` must still work exactly as before once called — the local `import torch` inside it is the
  only behavioural difference from before, and it has none (Python caches imports; a local `import torch`
  costs nothing after the first call in a process that already imported it elsewhere, e.g. every real pipeline
  process).
