# B32 — `doctor`: derive required Ollama models from the real profile/judge config

## Changes

- `src/omniscan/doctor.py` (only the card's three items; every other check untouched):
  - New `required_ollama_models(profile_paths=None, judge_paths=None) -> list[str]`, placed directly
    below `Status` because the module constant below it calls it at import time. It loads profiles
    (`load_profiles`), keeps only `enabled` ones (same filter as `pipeline/stages.py::build_stage`),
    resolves fallbacks with `resolve_fallbacks(enabled, profiles)` against the *full* dict (so a
    disabled profile still qualifies as a fallback target, exactly like `translategemma-12b-local`
    today), collects each enabled profile's `.model` plus its fallback's `.model` right after it, then
    appends the judge's model (`load_judge_config(...).model`) and dedupes keeping first occurrence.
    No `*-cloud` exclusion: every model in the list is checked the same way.
  - `REQUIRED_OLLAMA_MODELS` keeps its name and `tuple[str, ...]` type but is now computed at import
    time from the shipped files only: `required_ollama_models(default_profile_paths()[:1],
    default_judge_paths()[:1])` — i.e. `config/translation_profiles.toml` and `config/judge.toml`,
    ignoring any per-user override — with a comment stating it is the fixed machine-independent
    reference value. With today's shipped files it is `("gemma4:31b-cloud", "translategemma:12b")`.
  - `check_ollama_models` now calls `required_ollama_models()` with **no arguments** (shipped + user,
    the real merged behaviour) instead of iterating the constant. `CheckResult` shape, the
    `missing: a, b` WARN message and the `N models, all required present` OK message (`N` still counts
    `/api/tags` entries) are unchanged. A new first `try/except (OSError, ValueError)` around the
    derivation returns `CheckResult("ollama_models", "WARN", f"{type(exc).__name__}: {exc}")` so a
    broken config file cannot crash `omniscan doctor`.
  - Imports: `collections.abc.Sequence`, `omniscan.translate.judge_config` (2 names) and
    `omniscan.translate.profiles` (3 names). No import cycle (both translate modules only import
    `core.config`; `translate/__init__.py` is empty).
- `tests/unit/test_doctor.py` (ollama_models section rewritten under a `card B32` marker comment):
  - Helper `_use_config` writes temp `translation_profiles.toml` + `judge.toml` mirroring the shipped
    shape (two disabled profiles — one unreferenced, one a fallback target — plus one enabled profile
    whose fallback is the disabled one) and monkeypatches `doctor.default_profile_paths` /
    `doctor.default_judge_paths`, so `check_ollama_models`'s no-argument derivation is hermetic and
    machine-independent. The real user dir is never read.
  - `test_required_models_shipped_files_pinned` — the card's concrete current-reality check: no
    mocking, no tmp files, asserts `required_ollama_models() == ["gemma4:31b-cloud",
    "translategemma:12b"]` against the actual shipped config (enabled profile first, then its
    fallback; judge model deduped away).
  - `test_required_models_constant_is_shipped_defaults` — pins `REQUIRED_OLLAMA_MODELS ==
    ("gemma4:31b-cloud", "translategemma:12b")` (stays true even on machines with user overrides,
    since the constant reads shipped files only).
  - `test_required_models_disabled_profile_vs_disabled_fallback` — two temp profile files (also
    exercising the multi-file load order, like shipped-then-user) plus a temp judge file: the
    disabled-but-fallback profile's model is included (`fallback:12b` right after its parent's
    `main:31b`), the disabled-unreferenced profile's `alone:1b` is excluded, judge model appended
    last → `["main:31b", "fallback:12b", "judge:1b"]`.
  - `test_required_models_judge_model_not_duplicated` — judge model equals the enabled profile's
    model; result has it exactly once (also covers the explicit-argument form of the API).
  - `test_ollama_models_missing` / `test_ollama_models_all_present` — rewritten end-to-end on the
    mock transport using the new derived set: missing one → WARN `missing: main:31b-cloud`; both
    present → OK with detail `2 models, all required present`.
  - `test_ollama_models_broken_config_warns` — temp profile with `fallback = "missing"` so
    `resolve_fallbacks` raises; `check_ollama_models` returns WARN starting with `ValueError:` and
    containing `unknown fallback profile`, called directly (not via `run_all_checks`).
  - The old `test_ollama_models_missing`/`test_ollama_models_all_present` (built from the constant,
    with the stale `if n != "gemma4:12b"` filter) were replaced by the two above. The third reference
    to `doctor.REQUIRED_OLLAMA_MODELS` (in `test_run_all_checks_never_raises`) is untouched and still
    works: the constant keeps its name, and that test never asserts `ollama_models`' status.
- Nothing else: `core/**`, `translate/profiles.py`, `translate/judge_config.py`, `config/**`, other
  doctor checks and the CLI untouched.

The `gemma4:12b` false warning is gone: with the shipped files `required_ollama_models()` no longer

## Deviations

- `check_ollama_models` derives the required set **before** the `/api/tags` request (its own try
  block, ahead of the existing HTTP one). The card did not pin the ordering; this fails fast on a
  broken config and means a config error reports WARN even when Ollama is also unreachable (instead
  of the later FAIL). The HTTP-failure behaviour itself is byte-identical.
- The config-error catch is `(OSError, ValueError)`, mirroring `check_models`'s handler, not a bare
  `Exception` (the `run_all_checks` style the card also named): every documented loader failure
  (`load_profiles`/`load_judge_config` wrap invalid TOML and validation errors into `ValueError`;
  `resolve_fallbacks` raises `ValueError`) is covered, and `OSError` covers unexpected file-access
  failures. Anything else still propagates and is converted to FAIL by `run_all_checks`'s existing
  wrapper.
- Importing `omniscan.doctor` now reads the two shipped TOMLs (tiny, local) to build the constant;
  a repo checkout with an invalid shipped `config/*.toml` would fail at import instead of at check
  time. Accepted per the card's design (the constant must be deterministic at import time); the
  shipped files are repo content and covered by the pinned tests.
- `test_required_models_shipped_files_pinned` calls the no-argument form, which merges shipped +
  per-user config. It pins current reality, so a machine whose user override files change the
  enabled profile set would fail it — verified not the case here (see pre-flight above). The
  machine-independent shipped-only expectation is pinned separately via the constant test.
