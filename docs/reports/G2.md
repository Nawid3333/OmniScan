# G2 — Steady GPU load: background warm-up and a faster typeset fit loop

## Summary

Two changes, no behaviour change visible to users except wall-clock: (1) a `GpuWarmup` daemon
thread runs the exact op list from `docs/GPU_NOTES.md` (first convolution, 1×1 convolution,
transposed convolution, rfft2/irfft2 at both LaMa window sizes, bmm, bilinear-antialias
interpolation, synchronize) once per process, started by `build_vram_manager` on CUDA devices, so
the measured 9–14 s Composable-Kernel load and the 1–3 s first-FFT/GEMM/transposed-conv stalls
overlap with ingest and model loading — measured 11.7 s on the RX 9070 XT with the main thread's
first convolution afterwards at 0.001 s. (2) The typeset fit loop now memoises `getlength` per
call, skips sizes that provably cannot fit (a single word wider than the box; a line-count lower
bound), and caches fonts and measurements across calls for the default `load_font` path —
measured 72 679 → 16 075 `getlength` calls (22.1%) on the card's 60-region synthetic chapter,
with every layout bit-identical to the pre-G2 code.

## Changes

- `src/omniscan/gpu/warmup.py` (new): `GpuWarmup` — constructed with a `torch.device`, never
  raises, `start()` spawns one daemon thread (`gpu-warmup`) guarded by a start lock;
  `wait(timeout)`, `done`, `seconds` (`None` until done, `0.0` for non-CUDA devices), `error`
  (`"<ExceptionType>: <message>"` of the first failing step). The thread body does
  `torch.cuda.set_device` (after `_indexed()`, see Deviations 3), then, inside
  `torch.inference_mode()`, fp32: conv2d 3×3 on `[8,32,320,320]` with a `[64,32,3,3]` kernel,
  padding 1; conv2d 1×1 on the same input; `conv_transpose2d` `[1,64,64,64]`×`[64,32,4,4]`
  stride 2 padding 1; rfft2+irfft2 (`s=(512,512)`) on `[1,64,256,256]` and `[1,64,512,512]`;
  bmm `[4,128,128]`²; `F.interpolate` bilinear `antialias=True`; `torch.cuda.synchronize`. Each
  step has its own try/except → WARNING `"GPU warm-up step %s failed: %s"`, first failure kept in
  `error`, remaining steps still run; INFO `"GPU warm-up finished in %.1f s"` before the done
  event is set, so `wait()` returning implies the finish was logged. `start_warmup(device)` —
  one instance per `(process, str(device))` under a module lock, created and started on the
  first call, shared after.
- `src/omniscan/gpu/groups.py`: `build_vram_manager` now resolves the device once
  (`resolve_device(cfg.gpu.device)`, the same call `VramManager` made internally) and returns a
  `WarmupVramManager` — an annotation-only subclass carrying `warmup: GpuWarmup | None`
  (VramManager has no `__slots__`, so the card's module-level-variable fallback was not needed).
  When `cfg.gpu.warmup` and the resolved device is CUDA it calls `start_warmup(device)` before
  returning (non-blocking; the handle stays on `manager.warmup`); otherwise `warmup` is `None`.
  Import stays free of heavy libraries (warmup.py imports only torch).
- `src/omniscan/typeset/fit.py`: the fit loop keeps its signature, return values and geometry
  (`wrap_words` untouched); savings, in card order:
  1. `_MeasuredFont` — a per-call memo dict in front of every `font.getlength`, so repeated
     words/lines/`width` lookups measure once;
  2. sizes above `min_px` skip `wrap_words` when any word alone is wider than `max_w`
     (⟺ the old code's `too_wide`) or when
     `ceil(sum(word widths) / max_w) * line_height(size, line_spacing) > max_h` — exact float
     arithmetic on the unrounded sum, a lower bound on the wrapped height because every line
     advance is ≥ its words' advances (additive fonts, see Questions 1);
  3. `_default_font` (used only when `font_factory is load_font`) caches `load_font` results per
     `(str(path.resolve()), size)` (max 512, cleared when full) and measurements per
     `(resolved path, size, text)` (max 200 000, cleared when full) via `_CachedFont`;
     custom `font_factory` callers keep today's behaviour (per-call memo only).

## Deviations

1. **`WarmupVramManager` subclass instead of a module-level variable** — the card allowed a
   module-level var "only if `VramManager` uses `__slots__`"; it does not, so I used the simpler
   thing the card's phrasing implies: an annotation-only subclass declaring `warmup`. Runtime
   behaviour is identical to the card's spec (`manager.warmup`, `None` when disabled).
2. **`build_vram_manager` resolves the device itself** — previously the manager resolved
   internally; now the same `resolve_device` call happens in `build_vram_manager` and the result
   goes to both the manager and `start_warmup`, guaranteeing both land on one device. Same
   semantics, one call.
3. **Index-less CUDA devices are normalised (`_indexed()`)** — the real-GPU smoke with
   `gpu.device="cuda"` exposed that `torch.cuda.set_device` rejects an index-less
   `torch.device("cuda")` (`ValueError: Expected a torch.device with a specified index`), which
   would have silently disabled the warm-up for that spelling. The thread now targets
   `torch.cuda.current_device()` when the index is missing — the same device PyTorch ops use for
   an index-less device — and a test pins it. Not in the card; discovered by the smoke.
4. **The 1×1 conv and the interpolation reuse the 3×3 conv's `[8,32,320,320]` input** — the card
   fixed shapes for the convolutions, FFTs and bmm but not the interpolation input; sharing one
   allocation keeps the same op coverage with less memory churn.
5. **Test commands drop the card's extra `-q`** — pytest addopts already include `-q`; the extra
   one compounds to `-qq` and hides the pass/fail summary. Test selection is exactly the card's.

## Questions

1. **The fit-loop lower bound assumes word advances are additive.** It holds for all seven
   bundled fonts (PIL built without Raqm → basic layout, no kerning; verified) and the 300-case
   equality test pins it. If a font with cross-word kerning were ever bundled, the bound could
   skip a size that would have fit and change layouts. Worth a note in the typeset docs or a
   known-additive gate on the bound if exotic fonts ever land. (No action taken — no such font.)
2. **`gpu.device="cuda"` (index-less) means "the current device" everywhere** — on this machine
   the current device is `cuda:0`, the integrated GPU that crashes on the first kernel of the
   discrete-GPU wheel (`docs/gpu/device.py` docstring), while `"auto"` correctly returns the
   discrete GPU. The warm-up now matches that target, but the pipeline itself would also hit the
   iGPU. Should `resolve_device` map a bare `"cuda"` to the best discrete GPU, or should the
   config comment warn users off the bare spelling? (`core/**` and `gpu/device.py` are yours.)
3. **Should the warm-up result surface beyond logs?** Today it logs INFO `"GPU warm-up finished
   in %.1f s"` (and WARNINGs per failed step); `manager.warmup` exposes `seconds`/`error` for a
   future summary line or metrics key if you want one.
