# B23 — Job queue (persistent, resumable, with notifications)

## Changes

New module `src/omniscan/queue/`:

- **`store.py`** — `Job` dataclass, `JobStatus` / `STATUSES` / `KNOWN_STAGES`, `queue_db_path()` and
  `QueueStore` (SQLite, WAL): `add` (with all five validations), `get`, `list`, `claim_next`
  (`BEGIN IMMEDIATE`, priority desc / id asc, sets `running` + `attempts += 1` + `started_at`),
  `complete`, `fail` (requeue while attempts remain), `pause`, `resume`, `cancel`, `retry`,
  `requeue_running` (attempt refunded), `clear_finished` (done + cancelled only), `close`,
  context-manager. Timestamps stored as ISO-8601 UTC text, returned tz-aware. Illegal transitions raise
  `ValueError(f"job {id} is {status}, cannot {action}")`, unknown ids `KeyError(job_id)`.
- **`worker.py`** — `PermanentJobError`, `Executor` / `Notifier` type aliases, `QueueSummary`,
  `run_queue`: calls `requeue_running()` first (crash recovery), claims and executes one job at a time,
  maps `PermanentJobError` → fail without retry, any other `Exception` → fail with
  `"{type}: {exc}"` (retry while attempts remain), any other `BaseException` (e.g. `KeyboardInterrupt`)
  → `requeue_running()` + re-raise. Events `job_done` / `job_failed` / `job_retry` / `queue_empty`
  (the last only when the loop drained after at least one job). Every notifier call is wrapped; a
  broken notifier only logs a warning. `run_queue`'s docstring documents the one-worker-per-db limit.
- **`notify.py`** — `log_notifier` (INFO on `omniscan.queue`), `webhook_notifier` (POSTs
  `{"event", "job": null | {...}}`; uses the given `httpx.Client` or a short-lived one with the given
  timeout; HTTP errors and non-2xx responses are logged at WARNING and swallowed), `combine` (calls all
  notifiers in order, one raising does not stop the rest).
- **`executor.py`** — `stage_executor(cfg)`: module-level `STAGE_TABLE` (`ingest`, `slice`; stage
  instances are built lazily per call so importing the module — and `omniscan --help` — stays fast),
  unknown stage → `PermanentJobError(f"stage {name!r} is not implemented yet")` before anything runs,
  `chapters=None` on a chapter-less series → `PermanentJobError(f"no chapters found for series ...")`,
  then one `run_series` call per stage name in job order; a `failed` outcome raises
  `RuntimeError("chapter/stage: error; ...")` after that call, so later stage names are not run.
- **`src/omniscan/cli.py`** — added the `queue` command group (`add`, `list`, `run`, `pause`,
  `resume`, `cancel`, `retry`, `clear`) at the end of the file plus its imports; no existing command
  was touched. `--webhook` has `envvar="OMNISCAN_NOTIFY_WEBHOOK"`; `webhook_notifier` is imported into
  `omniscan.cli`'s namespace at module level so tests can monkeypatch it.
- **Tests** — `tests/unit/test_queue_{store,worker,notify,executor,cli}.py`, all CPU-only, covering
  every acceptance item of the card.
- **Docs** — README status-table row and a `### omniscan queue` subsection in `docs/USER_GUIDE.md`
  (with a `work_root/queue.db` row in the folder-layout table), using output from the commands below.

## Deviations

- **Stage table holds factories, not instances.** The card asks for a module-level dict
  `name → list of stage instances` while also asking for lazy stage imports to keep `--help` fast; the
  two conflict. `STAGE_TABLE` is module-level but maps `name → factory` building the instance list per
  executor call (`STAGE_TABLE[name]()`); the unknown-stage check and the "nothing ran on unknown stage"
  behaviour are unchanged.
- **`STATUSES`** was added next to `JobStatus`/`KNOWN_STAGES` in `store.py` so the CLI can validate
  `--status` (the card's interface list does not name it, but it adds nothing and changes nothing).
- **`queue run` on an empty queue** prints `queue is empty` and exits 0 — checked after the drain via
  `summary.finished` being empty, as the card describes.
- The CLI's `add` validates stage names itself (against `KNOWN_STAGES`, message on stderr, exit 2) as
  instructed; `store.add` also validates (its `ValueError` is mapped to exit 2), so API users get the
  same protection.
- **Stored error for `PermanentJobError`.** The card's worker spec pins the `{type}: {exc}` error
  format only for "any other Exception"; for `PermanentJobError` it just says "fail without retry". The
  worker uses the same `f"{type(exc).__name__}: {exc}"` format there, so `queue run` prints
  `job 1 failed: PermanentJobError: stage 'detect' is not implemented yet` (the card's CLI example shows
  it without the type name). The stage's own message is fully contained either way.

## Questions

- None open. One design note: `fail` keeps `started_at` from the interrupted attempt and does not
  clear `error` when requeueing (the card only pins `attempts`, `finished_at` and status); the error is
  cleared by the next `complete` or `retry`.
