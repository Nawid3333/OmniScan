## Deviations

1. **Per-pass execution order is chapter-major, not the acceptance-test-6 golden.** Test 6's golden
   reads `ingest(A) ingest(B) slice(A) slice(B) …` (stage-major), but the normative Part 2 requires
   one `run_series(stage_objects, …)` call per pass, and `run_series` is chapter-major
   (`ingest(A) slice(A) detect(A) ocr(A) ingest(B) …`). Chapter-major is also what makes the
   in-memory ctx (decoded strip shared between stages of one chapter) work, and matches the card's
   own report spec ("in chapter order, then stage order"). The implemented golden keeps the property
   test 6 actually cares about: each GPU group is acquired once per pass, never per chapter. The
   test asserts the real order and this is listed as a question below.
2. **`client.close()` added** in the queue executor and CLI `finally` blocks. The card did not
   mention closing the chat client; `OllamaClient.close()` exists (it closes the httpx client), and
   a long-running worker would otherwise leak connections.
3. **Explicit unknown-stage check in `cmd_run`.** The CLI builds the client by scanning
   `PASS_OF[name]`, so an unknown `-s` name raised `KeyError` before `plan_passes` could produce the
   specified `run: unknown stage 'x' (known: …)` message. `cmd_run` now validates the names against
   `STAGE_ORDER` first (same message, exit 2 as specified).
4. **`build_stage` translate/judge guarded block.** The missing-client check is a nested `if` inside
   `if name in ("translate", "judge")` so pyright can narrow `client` to non-None in the adapter
   constructors. Messages are exactly as specified.
5. **`queue add` default stage stays `slice`** (untouched per the card), but stages now run exactly
   as listed — so the default job fails on a fresh chapter unless `ingest` is also listed. The
   guide documents this; flagged as a question below.

## Questions

1. **Test-6 golden (execution order):** confirm chapter-major per pass is intended (it follows from
   the normative `run_series`-per-pass requirement; the acquire-once-per-pass property holds either
   way). If stage-major is wanted, that is a `core.stage` change and needs a card.
2. **Cloud-model naming vs `_needs_local_gpu`:** the card's rule is
   `endpoint == "local" and not model.endswith(":cloud")`, but the shipped cloud models are named
   `gemma4:31b-cloud` / `glm-5.3-flash:cloud` — the gemma4 one ends in `-cloud`, not `:cloud`. As
   written, the shipped judge (and the enabled `gemma4-31b-cloud` profile) therefore declare
   `OLLAMA_GROUP` although they run on Ollama's cloud through the local daemon. This is harmless
   (acquiring `ollama_local` only evicts local models and frees torch memory) and a test documents
   the current rule, but should the rule also treat the `-cloud` suffix as cloud?
3. **`queue add` default stages:** should the default change from `slice` to something runnable on a
   fresh chapter (e.g. `ingest slice`), now that a stage list is executed literally?
