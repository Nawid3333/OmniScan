# O1a — Catalog of every OCR model and size (PP-OCR v5/v6, PaddleOCR-VL, manga-ocr)

## Summary

The catalog gains the `hf` format (upstream-only Hugging Face model, pinned commit, per-file
sha256) and the descriptive fields `role`/`family`/`size_class`/`langs`/`recommended_for`/`notes`,
plus 26 new entries generated by the new `scripts/hf_catalog.py` from the live Hugging Face API:
6 PP-OCRv6 det/rec, 13 PP-OCRv5 (mobile det, server/base mobile rec + 10 per-language mobile recs),
3 PaddleOCR-VL, the 2 official PaddleOCR-VL GGUF builds and 2 manga-ocr models. `config/models.toml`
now has 34 entries (was 8), every one carrying `role` and language tags. Store/download/resolve/CLI
handle the new format (`.installed.json` marker with revision + verified file sizes;
`models verify --deep` re-hashes), and `models list` gains `--role`/`--lang` filters. The engines
that run the new models are card O1b; every new entry is `required = false`, `used_by = []`.

## Changes

- `src/omniscan/models/catalog.py`: `ModelFormat` gains `"hf"`. `ModelEntry` gains `role`
  (`Literal["detector", "text_line_detector", "recognizer", "vlm_ocr", "inpaint", "llm"] | None`),
  `family`, `size_class`, `langs`, `recommended_for`, `notes` (all defaulted, so the old entries
  stay valid) and `files: dict[str, str]` (hf: file name → sha256). `validate_for_format()` gains
  the hf branch: `upstream_repo`/`upstream_revision` (40 hex) and non-empty `files` required, every
  hash 64 hex, `size_mb > 0` — each error names the field/entry like the other formats.
- `src/omniscan/models/store.py`: `install_path` returns `<models_dir>/<id>` for hf like zip;
  `model_status(..., deep=False)` — hf needs the folder, a `.installed.json` whose `revision`
  equals the catalog pin and per-file sizes matching the recorded ones; `deep=True` re-hashes every
  file (a same-size-but-modified file becomes `corrupt`).
- `src/omniscan/models/download.py`: `_download_hf` — snapshot-download with
  `allow_patterns=list(entry.files)`, verify every file's sha256, on mismatch/missing delete the
  folder and raise `ModelDownloadError` naming the file, on success write `.installed.json`
  (`source: "upstream"`, `revision`, `installed_at`, `files_verified`, `file_sizes`) and return
  `"upstream"`. `remove_model` deletes the hf folder; `verify_models(..., deep=False)` passes
  `deep` through.
- `src/omniscan/models/resolve.py`: `local_model_source` matches hf entries by `upstream_repo`
  like zip entries (installed only, so a missing/corrupt copy returns `None`).
- `src/omniscan/cli.py`: `models list` gets `--role ROLE` / `--lang CODE` filters; the text row
  shows `role` and `langs`, the JSON object additionally carries `role`, `family`, `size_class`,
  `langs`, `recommended_for`, `notes`; `models verify` gets `--deep`.
- `config/models.toml`: header documents the hf format; the 8 existing entries get `role` (+family/
  size_class where meaningful) and `ocr-det-ppocrv5-server` gets `langs = ["en", "zh"]` (its model
  card lists them); 26 new `[[model]]` blocks appended (ids listed under "Repos included").
- `scripts/hf_catalog.py` (new): `uv run python scripts/hf_catalog.py REPO [--id --role --family
  --size-class --revision]` queries `?blobs=true` metadata (license, `cardData.language`, head sha)
  and the tree endpoint at the pinned revision (`lfs.oid` = sha256 for LFS files; small non-LFS
  files are downloaded and hashed), prints a ready `[[model]]` block validated against `ModelEntry`,
  never writes files, 404/other fetch failures → clear stderr message and exit 1; fetch is
  injectable (keyword `fetch=`) for tests.
- `docs/MODELS.md`: rewritten — formats section (zip/hf/ollama), the full OCR-stack table (id,
  role, languages, size, licence, upstream repo@revision, hardware needs), LLM table, install
  layout, licences, and the excluded-by-design list.
- `docs/USER_GUIDE.md`: `omniscan models` section updated (new columns, `--role`/`--lang`,
  `verify --deep`, the hf `.installed.json` marker semantics, new examples).
- Tests: `tests/unit/test_models_catalog.py` (+7 hf validation/files tests, real-catalog tests
  extended to all 34 ids), `test_models_store.py` (+7 hf status tests), `test_models_download.py`
  (+6 hf download tests), `test_models_resolve.py` (+3), `test_models_cli.py` (+5), and
  `tests/unit/test_hf_catalog_script.py` (new, 6 tests, canned JSON / fake fetch, no network).

Excluded, with reasons (no entries):

- **ONNX conversions** (`PaddlePaddle/PP-OCRv*_onnx*`, e.g. `PP-OCRv5_mobile_det_onnx`,
  `korean_PP-OCRv5_mobile_rec_onnx`): PyTorch weights only today; an onnxruntime engine is a later
  CPU-speed option (O1b+). Listed here per the card.
- **Third-party GGUF builds of PaddleOCR-VL** (non-`PaddlePaddle` uploaders): only the two official
  GGUF repos are cataloged; third-party builds are unaudited and would duplicate the official ones.
- **No `japan` or `chinese_cht` v5 safetensors repo exists** on Hugging Face (searched
  `author=PaddlePaddle&search=PP-OCRv5&limit=100`): Japanese is covered by the base v5 recogniser
  (plus manga-ocr for bubble crops), Traditional Chinese by the base v5 recogniser.
- **`PaddlePaddle/PaddleOCR-VL`'s `PP-DocLayoutV2/` layout subfolder**: not part of the VLM weights;
  excluded from `files` (noted on the entry).

## Deviations

1. **H1 is not merged**, so the hardware fields (`min_vram_gb`/`min_ram_gb`/`backends`/`cpu_ok`/
   `cpu_speed`) are left out of the catalog. The hardware numbers from card item 5 are recorded as
   docs-only text in the `MODELS.md` table (tiny/small 0.5 GB VRAM "fast", medium/server 0.8 GB
   "ok", PaddleOCR-VL 6–8 GB VRAM + 12 GB RAM "unusable", manga-ocr 1.5 GB + 8 GB "ok"; the
   detector and LaMa entries were not specified in the card → "pending H1").
2. **`notes` field added although the card lists it among the H1 fields.** Part 3 of this same card
   *requires* `notes` on every v6 rec and the GGUF entries, which cannot be satisfied without the
   field, so it was added now (default `""`, no effect on old entries). The remaining H1-gated
   fields stay out.
3. **"the three v5-based entries" — only two exist.** The card (Part 1 and acceptance test 1) says
   `recommended_for = ["ko"]` goes on three v5-based entries, but the catalog's third Korean-stack
   model is `detector-comic-text-bubble` (RT-DETR-v2, language-independent) — only
   `ocr-det-ppocrv5-server` and `ocr-rec-korean-ppocrv5-mobile` are v5-based, and both now carry
   `recommended_for = ["ko"]`. The real-catalog test asserts exactly that set. (Also asked below.)
4. **`langs` where the cards are silent** (all recorded in the entries' `notes`): the per-language
   v5 recognisers derive the code from the repo name per the card's rule (`en`, `th`, `el`,
   `arabic` → `ar`, `te`, `ta`); the script-named `latin`/`eslav`/`cyrillic`/`devanagari` models
   keep `langs = []` + a note (the card only allows enumerating Latin languages if the card lists
   them — it doesn't); `korean_PP-OCRv5_mobile_rec` lists no languages on its card, `ko` is
   name-derived (already the case before this card); `manga-ocr-base-2025`'s card lists no
   languages either — `["ja"]` was derived from the model's purpose (matching
   `kha-white/manga-ocr-base`, whose card does tag `ja`). The base v5 recognisers carry a note that
   the upstream v5 release also covers zh-Hant/Japanese/pinyin while their cards tag en+zh.
5. **Script details the card left open:** `.gguf` and `.jinja` were added to the model-file
   suffixes so the GGUF entries capture their weights + chat template; `size_mb` is Σ file sizes
   rounded up in decimal MB (the existing entries' convention); the script's generated `name`/
   `description` placeholders were replaced with real names and one-sentence descriptions when
   pasting, and `apache-2.0` was normalized to `Apache-2.0` (the existing entries' spelling).

## Questions

1. The card counts **three** v5-based entries for `recommended_for = ["ko"]`, but only two v5-based
   entries exist (`detector-comic-text-bubble` is RT-DETR-v2). Is the third one
   `detector-comic-text-bubble` (then the spec's wording should change), or was a third entry
   expected that doesn't exist?
2. Should the script-named v5 recognisers (`latin`, `eslav`, `cyrillic`, `devanagari`) get an
   enumerated `langs` list (the cards don't provide one), or is `[]` + the note the right
   representation until the O1c qualification suite measures them?
3. `manga-ocr-base-2025` got `langs = ["ja"]` derived from its purpose (its card tags no language).
   Confirm, or should derived languages always stay empty?
