- **New** `src/omniscan/hw/__init__.py` (empty), `hw/detect.py`: `GpuInfo`/`HardwareInfo` dataclasses,
  `classify_vendor`, `is_integrated`, `detect_hardware` (torch imported lazily inside; missing or

- `src/omniscan/cli.py`: new `omniscan hardware [--json]` command; `models list` text gains the
  `fit` column and indented reason lines (only for non-`ok` models that are not installed), the JSON
  gains `compatibility` per model and the top-level `hardware` object; `models download` gains
  `--force`, prints a warning line for every non-`ok` model and refuses `incompatible` ones
  (exit 1, nothing downloaded) without it. Nothing else in cli.py was touched; `core/**` and
  `gpu/*` untouched.
- Docs: README status row, USER_GUIDE (`### omniscan hardware`, `models` table updated),
  MODELS.md (requirement-field paragraph).
- Tests: `tests/unit/test_hw_detect.py`, `tests/unit/test_hw_assess.py` (new);
  `tests/unit/test_models_catalog.py`, `tests/unit/test_models_cli.py` (extended).

## Deviations

- **Rule 4's incompatible device value:** the card lists `device: "cpu"` for the CPU path but the
  `Compatibility` contract says `None` when incompatible; I followed the contract (`device: None`
  for every incompatible outcome, including `cpu_speed = "unusable"`).
- **Rule 4's `unusable` message:** the card defines the CPU-path message as `"runs on the CPU"`
  (+ `" (slow)"` for levels `slow`/`warn`); I apply it to all CPU-path outcomes, so `unusable`
  models read e.g. `incompatible: runs on the CPU`.
- **"or the previous VRAM message kept":** when a too-small GPU produced the VRAM message and the
  CPU path then refuses (no cpu backend / `cpu_ok = false`), I keep only the VRAM message and do not
  also append `"needs a supported GPU (cuda/rocm/mps); none found"` (that message only appears when
  no candidate GPU existed at all).
- **Disk check applies to every entry** ("regardless of the path"); cloud entries have
  `size_mb = 0`, so it never fires there.
- `mps` GPU `vram_gb` uses total RAM (per card) and `torch_build` becomes `"mps"` on an MPS-only
  machine; on an XPU-only machine `torch_build` stays `"cpu"` because the card's `TorchBuild`
  literal has no `xpu` member (the XPU GPUs still appear with backend `xpu`).
- The default `models_dir` for `detect_hardware(None)` resolves from `PathsConfig()` defaults (no
  TOML parsing); the CLI always passes `cfg.paths.models_dir` explicitly.
- `test_docs.py` was not modified (acceptance 6 says it must stay green — it is).

## Questions

1. `assess` reports the device string `"ollama"` for local Ollama models on any allowed path (GPU or
   CPU). Should the CPU fallback instead report `"cpu"` so the settings screen can distinguish "the
   LLM would actually be served on the CPU"? With the shipped catalog it never differs (all local
   LLMs are `unusable` on CPU).
2. The disk warning is raised to `warn` even for a `slow` CPU-fallback model — `slow` is arguably
   the more precise level and the disk message already says what changed. I chose "at least `warn`"
   literally (ok→warn, slow→warn). If the director prefers keeping `slow`, it is a one-line change
   in `_with_disk_warning`.
3. `classify_vendor`'s `intel` pattern includes the substring `arc`, which also matches words like
   "arch" in unknown names (card-specified). Fine as specified; noting it here in case a future GPU
   name trips it.
