**Status: DONE (verified; two verification sub-steps need the owner, see Questions).** This
continues the earlier WIP commit (`f036706`, which was stopped because the worktree then predated
main's run/job/final API — that premise is now false: the branch was updated onto `412c5b6` before
that WIP was committed, so `webui/src/api.ts` has `postRun`/`getJob`/`putFinalLine` exactly as the

## Changes
- `webui/src/run.ts` (new): `RunPhase`, `RunState`, `phaseOf` ("paused"/"cancelled" → "failed"),
  `POLL_INTERVAL_MS = 1500`, exactly per the card's interface.
- `webui/src/run.test.ts` (new): table-driven `phaseOf` test over all six `JobStatus` values, plus
  the `POLL_INTERVAL_MS = 1500` pin.
- `webui/src/RunButton.svelte` (new): props `{series, chapter, through, label?, onDone}`; idle/failed
  renders the button ("Retry" + red error `<p>` on failed); click → `postRun`, phase "queued", the
  response's `stages` shown immediately, `setInterval(getJob, 1500)`; each poll maps
  `phaseOf(job.status)`, sets `error = job.error` on failure, stops and calls `onDone` once on done;
  "queued"/"running" render as `running: ingest, slice, detect, ocr…`. A series/chapter prop change
  resets to idle and tears down polling (a `$effect` reading the two props, teardown =
  `stopPolling`; an `epoch` counter additionally invalidates a POST or poll that was already in
  flight across the switch, so no stale timer or state write survives a chapter switch).
- `webui/src/edit.ts`, `webui/src/edit.test.ts`: already completed in the WIP commit (accepted
  unchanged: `textByRegion`, `overlayStyle` reusing `alignLabel`; 6 tests).
- `webui/src/EditView.svelte` (new): loads ingest+layout (LayoutView's exact error/loading/empty
  structure, plus the `<RunButton through="typeset">` under the missing-layout message), then
  fetches final.json and inpaint.json as soft-optional (`Promise.allSettled`): missing final lines
  render as blank-but-editable overlays; a missing inpaint.json falls back to the raw page stack
  with `<RunButton through="inpaint">` above the pages (non-blocking). Background = InpaintView's
  raw stack + patch/fill layer verbatim, always fully clean — no reveal slider, and therefore no
  `clip-path` at all (it would be `cleanClipPath(100)` = a no-op inset; omitting it reads clearer,
  allowed by the card). Overlay: one box per layout item at `stripBoxToStackBox`, background
  `rgba(255,255,255,0.85)`, styled by `overlayStyle`, text from `textByRegion`. Click swaps in a
  same-box `<textarea>` (autofocused, caret at end); Enter-without-Shift or blur commits via
  `putFinalLine` (a "saving…" label at the box's corner while in flight); success updates
  `final.lines` locally so the div shows the saved text with no reload; failure shows the error in
  `<span style="color:#dc2626;">` next to the box and keeps the textarea open with the attempted
  text; Escape cancels back to the last-saved text. `commitEdit` re-checks `editingId` after the
  await so a blur-commit landing after the user moved to another region can neither double-PUT nor
  close the new editor.
- `webui/src/App.svelte` (modified): `"edit"` added to the view union, `EditView` imported, an
  **Edit** nav button between Layout and Filtered, and the `{#if view === "edit"}` route.
- Six views (modified, per the card's table — original missing-data text kept, button added under
  it): `SlicerView` (`through="slice"`), `OcrView` (`"ocr"`), `TranslationView` (`"ocr"`),
  `InpaintView` (`"inpaint"`), `LayoutView` (`"typeset"`), `ReaderView` (`"export"`). No
  translate/judge button anywhere.

browser automation available in this session — see Questions), so the UI-facing behaviours were
verified at the level the card's own backend-verification used: the exact HTTP calls the components
make, driven from Node against the live server.

1. **Real run lifecycle (what `RunButton` drives):** `KoreanScan/Chapter 1` natively has
   `ocr.json` missing (verified via the API — the exact missing state `OcrView`/`TranslationView`
   render the button for; no artifact deletion needed). `POST …/run {"through":"ocr"}` →
   `202 {"job_id":2,"stages":["ingest","slice","detect","ocr"]}`; then 1.5s polls showed
   `status=running … attempts=1/2 error=null` for ~18s, then `status=done`, then
   `GET …/ocr` → 200 with a real regions artifact. I.e. button-click → queued/running text →
   artifact exists → view reload is exactly the sequence this component performs.
2. **Real final-line edit persistence (what `EditView` commits):** picked region `r0002` of
   `SoloLeveling/Chapter 1` (decision `"pick"`, text "A passage connecting this world to another
   dimension..."); `PUT …/final/r0002` with the same text → `200` `{"decision":"manual",
   "rationale":"edited in the debug UI","sources":[],"flags":[]}`; a fresh `GET …/final` (re-read
   from disk) confirmed the line now reads decision `"manual"` with the text unchanged (I edited
   with the identical text and then PUT it once more — the content-identical round trip proves
   persistence without altering the real chapter's translation content; the decision flip to
   "manual" is the card's own persistence observable). `PUT` for an unknown region → `404`

  `font-family: sans-serif`) — additive, acceptance substrings unaffected.

  card does not specify a failure policy for polls; a single dropped request should not flip the
  button to failed). Persistent failure keeps polling at 1.5s — the phase never lies.
