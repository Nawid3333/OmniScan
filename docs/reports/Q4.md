## Equivalent mutants

- `download.py` #37 — `update/download.py:90`, `checksums[asset.name]` -> `checksums.get(asset.name, "")`.
  The preceding `if asset.name not in checksums: raise UpdateError("SHA256SUMS has no entry ...")`
  makes the fallback second argument unreachable; when the name *is* present, `.get` returns the
  same digest. Output cannot change. The existing `test_download_update_missing_sums_entry` pins
  the raise, so the guard the mutant would bypass is itself covered.

## Questions

1. **Harness hazard: stale `__pycache__` can poison verdicts.** `scripts/mutate.py` writes the
   mutant, runs pytest (which compiles the mutated module into `__pycache__`), then restores the
   original. If the restore lands in the same whole second as the mutation and the mutant keeps
   the same byte size, the restored file's `(mtime, size)` still matches the pyc header
   (`flags: 0` = timestamp validation) and Python keeps executing *mutated* bytecode for later
   tests in the same process. Evidence: a `resolve.py` survivor that disappeared after deleting
   `__pycache__`; a pyc whose header matched the restored source. **Workaround applied:** both
   mutants files set `PYTHONDONTWRITEBYTECODE=1` at module load (the harness loads them with
   `runpy` and passes `os.environ` into the pytest subprocesses). **Suggestion for the
   harness (director-owned):** set that env var in `scripts/mutate.py` `run_tests` itself, or
   invalidate pycs by touching restored files. This hazard produced at least one wrong verdict
   during the first pass (#29 was "KILLED" in a contaminated run and correctly SURVIVED on the
   clean re-run).
2. **Harness hazard: interrupted runs can leave CRLF-corrupted production files.** An
   interrupted session left `src/omniscan/update/github.py` with CRLF line endings (git showed no
   content change, but every `old` snippet containing `\n` stopped matching — `occurs 0 times`).
   Fixed by normalizing back to LF (byte-identical to HEAD). **Suggestion:** read/write target
   files as bytes in `scripts/mutate.py` so mutations and restores are byte-exact.
3. **Withdrawn anomaly:** during debugging I briefly suspected the interpreter evaluated
   `403 > 400` incorrectly. That was my own arithmetic error — `403 > 400` is simply true; the
   clean re-runs' SURVIVED verdict for #29 was correct and pointed at a real test gap (HTTP
   exactly 400), now closed. No interpreter issue; the leftover probe file was deleted.
4. Both `>= 400` mutants (#29, #44) existed because the suites only exercised 403/429/404/500.
   The new tests pin the 400 boundary in both places.
