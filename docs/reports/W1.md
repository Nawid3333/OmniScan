# W1 — model-watch: find new upstream model releases (script + GitHub Action)

## Changes

- `scripts/model_watch.py` (new): `Change`/`WatchConfig`/`OrgWatch`/`CatalogEntry` dataclasses,
  `load_watch_config`, `check_entries`, `find_new`, `render_report`, `main`, and the default
  `http_fetch` (httpx, 30 s timeout, `User-Agent: OmniScan-model-watch`, optional `HF_TOKEN` bearer,
  2 retries on 5xx/transport errors with `0.5 * 2**attempt` s back-off, injectable `sleep` and
  `transport` for tests). Exit codes 0 / 3 (`--fail-on-change`) / 2 (bad arguments, unreadable
  config, unwritable output).
- `config/model_watch.toml` (new): the four orgs and patterns exactly as the card specifies,
  `ignore = []`.
- `.github/workflows/model-watch.yml` (new): Mondays 06:00 UTC + `workflow_dispatch`;
  `permissions: contents: read, issues: write`; one job on `ubuntu-latest` that captures the
  script's exit code (`set +e … code=$? … set -e`), fails the job only on 2, on 3 creates the
  `model-watch` label and comments on (or opens) the issue, and always uploads `model-watch.md` /
  `model-watch.json` as artifacts. `GH_TOKEN` from `secrets.GITHUB_TOKEN`, `HF_TOKEN` optional.
- `tests/unit/test_model_watch.py` (new): 38 tests — config parsing incl. 9 bad-input cases,
  `check_entries` kinds/warnings/sharing, `find_new` filtering/ordering/warnings, golden
  `render_report` (one of each kind + no-changes + determinism), `main` exit codes/outputs/
  `--offline`, HF_TOKEN bearer + secrecy, MockTransport retry tests, and the workflow YAML.
- `docs/MODELS.md`: appended a "Model updates" section (what the Action checks, what to do with a
  report, how to run it locally, exit codes).

## Deviations

1. **`main` does not call `src/omniscan/models/catalog.py:load_catalog`.** The card's workflow
   command runs `uv run --no-project --with httpx` — that environment has no pydantic, so importing
   `omniscan.models.catalog` (`ModelEntry`) at runtime would crash the CI job. The script instead
   reads the catalog with `tomllib` into a minimal 4-field `CatalogEntry` (id, format,
   upstream_repo, upstream_revision — all the watch needs). The card's interface is kept exactly at
   the type level: `check_entries(entries: Sequence[ModelEntry], fetch: Fetch)` with a
   `TYPE_CHECKING`-only import, and `check_entries`/`find_new` accept real `ModelEntry` objects
   (the unit tests pass them). Verified with the exact CI command above.
2. **The workflow had no existing sibling** — `.github/workflows/` did not exist on this branch
   (no prior CI), so `model-watch.yml` establishes the style (permissions block, pinned
   `actions/*`/`astral-sh/setup-uv` versions, no `continue-on-error`).
3. **The report table shows the first 8 hex of a revision** (`old → new`); the JSON artifact
   carries the full 40-hex shas, which is what a catalog update copies.

## Questions

1. The card's pattern `PP-OCRv*` matches every v3/v4/v5/v6 repo **and all `*_onnx` builds** — the
   live run reported 66 `new` PaddlePaddle repos (e.g. `PP-OCRv3_mobile_det`,
   `PP-OCRv5_server_rec_onnx`). Options: narrow the patterns (`PP-OCRv5*`, `PP-OCRv6*`) or populate
   `ignore` after the first issue. I shipped the patterns exactly as specified.
2. The HF listing search (term `OCR`, `limit=100`, sorted by lastModified) did not return the
   `*_safetensors` repos within the first 100 results, so "new" detection for those names depends
   on the search ranking. Pin drift (`updated`/`missing`) is unaffected — it queries each repo
   directly. If it matters, a future card could page through the listing.
