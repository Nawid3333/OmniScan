## Deviations

1. **`workflow_dispatch:` added** (not in the card's sketch): matches `model-watch.yml`'s
   convention and lets the director re-trigger the workflow after the merge without waiting for
   another push.
2. **Job-level `defaults: run: shell: bash` added**: GitHub's default `run` shell on Windows is
   pwsh, which works but handles quoting differently; pinning bash (Git for Windows is
   preinstalled on the runners) makes `-m "not gpu"` and the `&&` chain behave identically on all
   three OSes.
3. **Local acceptance commands ran with `uv run --no-sync`** instead of the card's bare
   `uv run ...` — every sync-mode `uv run` in this worktree currently fails before the command
   runs (see the environment note below). With `--no-sync` the suite runs against the
   machine-standard environment and the worktree's own `src/` (the `omniscan` install is
   editable), so the result is equivalent.
4. **No push performed.** CLAUDE.md's hard rule ("never push, never touch `main`") plus the card's
   parenthetical ("not a manual `git push` to `origin` — that stays the director's job") and the
   fact that no card branch has ever existed on `origin` all read the same way: the commit stays
   local and the director pushes after merging. If the director instead wants the `P2` branch
   itself on `origin`, that is a single `git push -u origin P2` from this worktree.

## Environment note (found while testing; not fixed — outside this card's file list)

- This worktree's `.venv` is a **junction to `V:\OmniScan\.venv`** (`pyvenv.cfg`, `Scripts` and
  `Lib/site-packages` all `os.path.realpath` to the main checkout — omni_builder's
  storage-saving design). Any uv-managed sync in a worktree therefore operates on the main
  checkout's environment.
- P1 changed `pyproject.toml` (the extras table), so uv considers the installed `omniscan`
  package stale and wants to reinstall it on any sync; the reinstall first removes
  `Scripts/omniscan.exe`, which the owner's live `omniscan serve` (main checkout, started
  2026-09-23 18:22) holds with an exclusive handle → `WinError 32` / os error 32 on every
  sync-mode `uv run` in this worktree (a plain rename of the file is blocked the same way).
- That lock was **protective**: the attempted local `uv sync --extra cpu` (this card's own CI
  command, run as evidence) had resolved and downloaded the cpu wheels from the
  `pytorch-cpu` index (torch 120.1 MiB + torchvision 1.3 MiB — the committed lock's `cpu`
  resolution works on Windows) and was about to **replace the main checkout's rocm torch with
  the cpu build** when the lock stopped it. Recommendation recorded for future builders: never
  `uv sync --extra <backend>` in a worktree while `.venv` junctions to the main checkout — use
  `uv run --no-sync` for suite/lint/type-check runs (the worktree's source is what differs, and
  the editable install already points at it).
- Side observation: two leaked `bash.exe` polling loops from 2026-09-20 19:24 (waiting for
  `OmniScan-wt/G2` and `/Q5` commits) are still in the process table — harmless, but the
  director may want to reap them.
